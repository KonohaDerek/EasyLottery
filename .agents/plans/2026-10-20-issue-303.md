# Stable lottery participant identity — #303

## Outcome and boundaries

Use a stable identity tuple `(platform, account ID)` for automatic participant deduplication and per-account cooldown when the provider supplies an ID. Display names remain presentation and explicit allow/deny rule values; they do not merge participant accounts.

Keep the existing REST route and YouTube protocol. Add the YouTube channel ID as an additive optional response field, and keep participant identity optional so existing hand-entered and imported data remains valid. Cross-platform identities remain separate unless an explicit verified linking flow already supplies a link; this change does not infer or apply links.

## Bounded implementation

1. Project `AuthorDetails.ChannelId` (falling back to `Snippet.AuthorChannelId`) as `authorId` and `platform: youtube`; assert the additive API response contract.
2. Add optional participant identity and normalize platform names while preserving the provider account ID exactly.
3. Deduplicate known participants and apply cooldown by platform + account ID. If an incoming message lacks either stable identity field, do not merge participants by name or attribute account cooldown to a guessed name.
4. Preserve explicit name-based keyword/allow/deny behavior. Extend JSON/CSV participant imports and exports with optional platform/account ID fields; parse stable IDs only from canonical YouTube channel profile URLs in Studio exports. Handles and unrecognized links remain ID-less.
5. Add unit/API coverage and a Playwright test with mocked messages. No real account or provider call.

## Non-goals and risks

- No database/schema migration: lottery state remains in the current client-side workspace, and older records have no identity metadata.
- No change to the legacy Blazor rollback route, identity-link protocol, Passkey, payment, SMTP, or native OBS behavior.
- Older JSON/CSV remains accepted. New CSV columns are additive; new JSON properties are optional. Older API payloads without an ID remain usable, with conservative no-merge behavior.
- Cooldown without an account ID cannot be attributed reliably; it is not recorded against a guessed name, avoiding false blocks for homonyms.
- No account IDs or messages are added to server logs. Existing chat status/errors remain the operational signal.

## Verification and rollback

Run focused and full Vue unit tests, TypeScript check, Vite build, focused API tests, the lottery Playwright spec against mocked endpoints, strict OpenSpec validation, and inspect the complete diff. After pushing and opening a Ready PR, verify all CI checks for the final commit.

Rollback is a source revert. The API change is additive; old clients ignore the new fields, old participant JSON/CSV remains importable, and no persisted server data is migrated. Do not merge or deploy.
