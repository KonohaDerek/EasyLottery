# 核心抽獎持久歷史

## 新增需求

### Requirement: 保存完整抽獎當下快照
系統 MUST 為每次新核心抽獎在抽選前建立穩定抽獎識別碼，並將抽中籤、完整抽獎當下參與籤名單及版本化規則快照與結果一併持久保存。參與籤快照 MUST 保留既有籤 ID、lotteryGroupId、顯示名稱、既有外部 platform/accountId（若存在）、等級、分組、標籤及依既有 `isWinner` 規則判定的資格狀態。規則快照 MUST 保留演算法版本、資格與群組得獎政策版本、合格籤數、首個剩餘獎項政策，以及抽獎當下完整獎項順序。

#### Scenario: 保存含外部身份及排除籤的合成名單
- **WHEN** 管理員完成抽獎並提交一份含合成平台身份、合格籤與已得獎排除籤的快照
- **THEN** 系統保存完整名單順序、外部身份、資格狀態、winnerParticipantId 與規則快照
- **AND** 只保存 Participant 現有欄位，不保存憑證、聊天室訊息或額外敏感欄位

#### Scenario: 後續名單編輯不改寫歷史
- **WHEN** 已保存結果後，管理員修改目前名單、外部帳號、標籤、分組或資格
- **THEN** 已保存的抽獎紀錄仍保留抽獎當下的值

### Requirement: 保存操作冪等且可安全對帳
系統 MUST 對相同抽獎識別碼與完全相同的結果及快照冪等回傳同一紀錄。相同識別碼但得獎結果、任一規則欄位、參與籤、外部身份或順序不同 MUST 回傳衝突。保存結果不明時 MUST 先以同一識別碼查詢；不得重新抽選。

#### Scenario: 相同 payload 重送
- **WHEN** 相同抽獎識別碼與完全相同的完整快照再次送達
- **THEN** 系統回傳已保存紀錄且不建立第二筆

#### Scenario: 同識別碼但外部身份或規則不同
- **WHEN** 同一識別碼搭配被修改的帳號識別或抽獎規則快照送達
- **THEN** 系統回傳衝突，保留原本完整快照

#### Scenario: 保存回應不明
- **WHEN** 用戶端無法確認保存結果
- **THEN** 用戶端先查詢原識別碼；只在查到完全相同記錄或明確查無記錄後決定下一步
- **AND** 網路錯誤、未授權、權限不足或資料不一致時不重新抽選也不以新識別碼重送

### Requirement: 管理名單存取受控且採分頁
系統 MUST 限管理員查詢完整參與名單。一般歷史列表 MUST 僅回傳必要摘要並分頁，不能包含完整名單或外部帳號。單筆名單查詢 MUST 分頁且每頁不超過 100 張籤。

#### Scenario: 公開或 OBS scoped session 查詢名單
- **WHEN** 匿名用戶或 OBS scoped token 查詢抽獎紀錄、摘要或參與名單
- **THEN** 系統拒絕請求且不回傳參與者資訊

#### Scenario: 管理員載入列表與單筆名單
- **WHEN** 管理員瀏覽抽獎歷史
- **THEN** 列表只取得分頁摘要
- **AND** 只有明確開啟單筆紀錄時才載入其規則與參與名單頁面

### Requirement: 不回填舊資料
系統 MUST NOT 從目前參與名單、瀏覽器儲存或其他來源推測並回填核心抽獎歷史功能啟用前未保存的抽獎結果。

#### Scenario: 歷史尚無保存紀錄
- **WHEN** 管理員開啟紀錄頁且沒有持久化結果
- **THEN** 系統顯示沒有已保存紀錄，不以目前名單合成舊結果
